# 员工列表完整分页优化设计

## 目标

完善员工管理列表的服务端分页体验，使分页状态可恢复、参数可校验、筛选切换可靠，并避免数据变化后停留在无数据的越界页。

## 范围

- 员工管理列表支持每页 10、20、50、100 条，默认 20 条。
- `page`、`pageSize` 与现有筛选条件统一保存在 URL 查询参数中。
- 任意筛选条件或每页条数变化时回到第 1 页。
- 修复“参与绩效”筛选变化后不一定重新请求列表的问题。
- 当前页超过最新总页数时，自动跳转到最后一个有效页。
- 上一页和下一页在边界状态禁用。
- 分页区显示当前页、总页数和总条数，最多展示 5 个连续页码。
- 前后端均对分页参数进行归一化，避免非法页码或页大小进入数据库查询。

## 前端设计

### URL 状态

`useEmployeeFilters` 增加 `pageSize` 字段和 `setPageSize` 方法。

- `page` 解析为大于等于 1 的整数，否则使用 1。
- `pageSize` 仅接受 10、20、50、100，否则使用 20。
- 修改 `pageSize` 时，与其他非页码筛选一样将 `page` 重置为 1。

### 数据请求

`useEmployeeList` 直接使用 `filters.pageSize`，不再维护重复的固定页大小常量。请求依赖包含所有参与请求构造的筛选字段，包括 `binding`。

列表请求成功后，如果 `total > 0` 且当前页超过 `ceil(total / pageSize)`，调用页码修正回调跳到最后有效页，不展示越界请求返回的空列表。页码修正后由 URL 状态变化触发下一次请求。

### 分页界面

分页区包含：

- 当前页/总页数与总条数；
- 每页条数选择器；
- 上一页、最多 5 个连续页码、下一页；
- 首页时禁用上一页，末页时禁用下一页。

列表不足一页时仍显示总数和每页条数选择器，但隐藏无意义的页码导航。

## 后端设计

Controller 将分页参数统一归一化：

- `page` 最小为 1，非法值回退到 1；
- `pageSize` 仅接受 10、20、50、100，非法值回退到 20；
- Service 继续通过 `limit`、`offset` 和独立 `count` 查询实现服务端分页。

Service 仍接收已经归一化的数字参数，不增加新的业务职责。

## 错误与边界

- 手工输入 `?page=-1`、`?page=abc` 时按第 1 页处理。
- 手工输入不支持的 `pageSize` 时按每页 20 条处理。
- 删除、停用或筛选导致最后一页消失时，自动回到新的最后一页。
- 总数为 0 时保持第 1 页，不产生第 0 页。
- 快速切换筛选沿用现有 loading 和错误提示机制。

## 测试

- 单元测试分页参数归一化函数。
- 单元测试 URL 筛选状态包含 `pageSize`，且非页码条件会重置页码。
- 单元测试员工列表请求包含 `binding` 和动态 `pageSize`。
- 单元测试后端 Controller 对非法 `page/pageSize` 的归一化。
- 运行员工管理相关测试、前后端 TypeScript 类型检查。

## 非目标

- 不抽取全项目通用分页框架。
- 不修改其他业务列表的分页方式。
- 不实现跨页勾选；员工批量操作仍只针对当前页选中项。
- 不引入新的状态管理或数据请求库。
