## 1. 考核模板管理

### 当前逻辑

| 功能 | 状态 |
|------|------|
| 模板 CRUD（创建/查询/详情/编辑/停用） | ✅ 完整 |
| 维度权重校验（求和=1） | ✅ |
| 指标满分值校验（求和=100） | ✅ |
| 创建/编辑时先删后插 | ✅ |
| 模板列表过滤（关键词/岗位/状态） | ✅ |
| 模板预览 | ✅ |

### 已发现问题

#### 1.1 编辑时先删后插，没有事务包裹

**位置**：`assessment-template.service.ts` — `update()` 方法

**问题**：先 `delete` 旧维度和指标，再 `insert` 新数据，但整个过程没有包裹在数据库事务中。如果中间某步失败，模板的维度和指标数据会丢失或处于不一致状态（维度删了但指标没删完，或维度删了但新数据没插入成功）。

**建议**：使用 Drizzle 的 `db.transaction()` 包裹整个更新逻辑。

#### 1.2 校验只在前端和后端 Service 执行，缺少数据库约束

**问题**：维度权重和=1、指标满分=100 的校验纯由业务代码控制，数据库层面没有对应的 CHECK 约束。如果未来有其他入口绕过 Service，一致性无法保证。

**建议**：在 Drizzle schema 中增加维度级和指标级的约束，或至少透传此限制文档。

#### 1.3 模板类型扩展性受限

**问题**：`type` 字段在共享类型中硬编码为联合类型 `'monthly' | 'probation'`。未来如需增加 `quarterly` / `yearly` / `project` 等类型，需同时修改 schema、共享类型、前端过滤逻辑。

**建议**：现有设计对小规模系统够用。如未来需要频繁扩展，可引入类型配置表。

#### 1.4 模板停用后缺少「启用」操作

**问题**：提供了 `deactivate`（停用），但没有对应的 `activate`（重新启用）。一旦停用只能通过数据库直接修改或重新创建模板。

**建议**：对称增加 `PATCH /:id/activate` 接口。

#### 1.5 模板列表返回字段中缺少维度和指标数量

**问题**：列表接口只返回模板基本信息，前端如果要展示"此模板有 X 个维度 Y 个指标"需要额外调用详情接口。

**建议**：在列表查询中通过子查询或 JOIN 统计每个模板的维度数和指标总数，作为额外字段返回。

## 2. 员工模板绑定

### 当前逻辑

| 功能 | 状态 |
|------|------|
| 绑定列表查询（多条件过滤 + 分页） | ✅ |
| 批量绑定员工 | ✅ |
| 自动失效旧绑定（换绑） | ✅ |
| 解绑 | ✅ |
| 绑定历史 | ✅ |
| 审计日志 | ✅ |

### 已发现问题

#### 2.1 换绑逻辑没有校验新绑定是否已存在周期性冲突

**位置**：`employee-binding.service.ts` — `create()` 方法

**问题**：当前换绑逻辑是：员工已有 active 绑定 → 将其设为 inactive → 创建新 active 绑定。但缺少对生效时间重叠的校验。

如果旧绑定生效月份 `2025-01`，新绑定生效月份 `2024-12` → 旧绑定被失效，但 `2024-12` 的考核可能已经发布。

**建议**：在换绑时增加逻辑：如果目标月份 ≤ 旧绑定生效月份，应给出警告提示"该操作可能导致已发布的考核数据异常"。

#### 2.2 绑定历史中绑定人只显示 user ID

**问题**：`BindingHistoryItem` 类型中的 `operatedBy` 字段是 user_profile 类型（user_id），前端展示时只能看到 ID，无法直接看到操作人姓名。

**建议**：History 接口 JOIN 操作人姓名，或前端通过 user_profile 的 displayName 能力展示。

#### 2.3 解绑操作没有校验是否存在未完成的考核实例

**问题**：解绑绑定记录时，该员工可能已有 `self_review` / `supervisor_review` / `pending_sign` 等未完成的考核实例。

**建议**：解绑时查询该员工是否存在未完成实例，若有则提示"该员工有待完成考核，解绑后不影响已有考核，但不会再生成新考核"。

#### 2.4 绑定列表不支持按岗位过滤

**问题**：查询条件不支持按员工岗位（position）过滤。模板本身是按岗位配置的，按岗位查看绑定关系是合理需求。

**建议**：增加 `position` 筛选参数。

## 3. 考核发布管理

### 当前逻辑

| 功能 | 状态 |
|------|------|
| 待考核员工列表 | ✅ |
| 批量发布（全量/按人） | ✅ |
| 指标快照（发布时从模板复制） | ✅ |
| 发布时单员工调整指标 | ✅ |
| 考核实例列表（状态过滤 + 分页） | ✅ |
| 实例调整指标（发布后修改） | ✅ |
| 实例解锁（状态回退） | ✅ |
| 审计日志 | ✅ |

### 已发现问题

#### 3.1 发布时没有校验重复发布（同员工同月份）

**位置**：`assessment-publish.service.ts` — `publish()` 方法

**问题**：对于同一个员工同一个考核周期，如果重复点击发布，会生成**两个**考核实例。当前没有查重逻辑。

**建议**：在发布前查询 `assessment_instance` 表中是否已存在 `employeeId + period` 的记录，若存在则跳过或提示。

#### 3.2 调整指标丢失维度归属（调整项维度权重写死为 0）

**位置**：`publish()` 方法中 `adjustmentsForEmp` 的处理，以及 `adjust()` 方法

**问题**：当发布时对某员工做了指标调整，调整后的指标快照的 `dimensionName` 硬编码为 `'调整项'`，`dimensionWeight` 硬编码为 `'0'`。这意味着：

1. 调整后的指标失去了维度分组语义，在考核详情页中所有调整指标都归入"调整项"维度
2. 权重为 0 导致该指标不参与维度加权计算

这与"仅对单个考核月做微小调整"的预期不符。

**建议**：调整 API 支持传入 `dimensionName` 和 `dimensionWeight`，或者提供"使用模板 + 局部覆盖"的调整模型，而不是整体替换。

#### 3.3 adjust() 同样硬编码维度信息（同上 3.2）

#### 3.4 解锁的状态回退链不完整，且不重置评分数据

**问题**：解锁后：
- 从 `pending_sign` 回退到 `supervisor_review`：上级评分记录还在但可以重新提交
- 从 `supervisor_review` 回退到 `self_review`：自评记录还在但可以重新自评

**建议**：解锁时应当重置对应的评分草稿状态（如将 `isDraft` 重置为 true），避免回退后用户看到"已提交"但实际状态已回退的困惑。

#### 3.5 实例列表缺少上级姓名

**位置**：`listInstances()` 方法

**问题**：列表查询中 `supervisorName` 字段直接赋值为 `row.supervisorId ?? ''`，显示的是 user ID 而非姓名。

**建议**：JOIN 上级的 employee 表获取姓名。

#### 3.6 发布时未发送飞书通知

**预期**：根据产品设计（`app-info.json` 用户故事），"批量发布后生成考核实例，状态变为自评阶段并通知员工"。但 `publish()` 方法未调用飞书消息能力通知员工。

**建议**：在发布成功后，遍历目标员工 ID，调用飞书消息能力发送考核通知（参考催办功能的实现方式）。

#### 3.7 adjust 允许 draft 状态但从未使用

**问题**：`adjust()` 方法检查允许的状态包含 `draft`，但其余地方从未将考核实例状态设为 `draft`。发布时直接设为 `self_review`。

**建议**：要么移除 `draft` 的条件检查，要么在发布时提供"草稿发布"选项。

## 4. 考核操作流程

### 当前逻辑

| 功能 | 状态 |
|------|------|
| 考核详情（含指标、评分、签名状态） | ✅ |
| 自评暂存/提交 | ✅ |
| 上级评分暂存/提交（含自动算分） | ✅ |
| 签名确认（员工/上级各自签名 → 完成） | ✅ |
| 审计日志 | ✅ |

### 已发现问题

#### 4.1 自评提交后缺乏驳回能力

**问题**：员工提交自评后状态直接从 `self_review` 变为 `supervisor_review`。如果上级想退回让员工修改，当前没有"驳回"功能，只能通过管理员解锁回退。

**建议**：增加"驳回自评"功能（Supervisor 角色），驳回后状态回到 `self_review`，并在审计日志中记录驳回原因。

#### 4.2 评分 upsert 模式存在并发风险

**位置**：`submitSelfRating()`、`submitSupervisorRating()`

**问题**：每次提交是对每个指标 `select → 存在则 update / 不存在则 insert`，不是批量操作也不是原子 upsert。高并发下可能产生重复记录。

**建议**：在 `(instance_id, indicator_snapshot_id, rating_type)` 上建唯一约束，数据库层保证不重复。

#### 4.3 自评没有校验是否已提交

**问题**：即使当前状态已经是 `supervisor_review`（表示自评已提交），只要有 `instance_id` 存在，就可以继续调用该方法。评分数据会被覆盖。

**建议**：在提交前检查当前状态，如果已经是 `supervisor_review` 或之后的状态，应拒绝修改并提示"自评已提交，如需修改请联系管理员解锁"。

#### 4.4 上级评分提交后没有校验 user 是否真是此员工的 supervisor

**位置**：`submitSupervisorRating()`

**问题**：方法接收 `userId` 但不校验该用户是否确实是此考核实例员工的上司。

**建议**：从 `employee` 表中查询该员工的 `supervisorId`，与当前 `userId` 比较，不一致则抛出 403 Forbidden。

#### ★ 4.5 【P0】权重在评分计算中未参与（严重的业务逻辑缺陷）

**位置**：`submitSupervisorRating()` 方法

**问题**：`submitSupervisorRating()` 中的总分计算是简单的分数累加 `body.ratings.reduce((sum, r) => sum + r.score, 0)`，完全没有使用维度权重（`dimensionWeight`）。这意味着：

1. 权重字段被存储但未被使用
2. 所有指标都是等权重的，权重配置失去了意义

这是一个**严重的业务逻辑缺陷**。

**建议**：修改总分计算逻辑为加权平均：
- 按维度分组
- 每个维度的加权得分 = 维度内指标得分之和 / 维度内指标满分之和 × 维度权重 × 100
- 总分 = 各维度加权得分之和

或更简单：指标得分 × 维度权重 的累加。

#### 4.6 等级计算基于简单总分，阈值硬编码

**问题**：等级计算基于总分数值（S/≥90, A/≥80, B/≥70, C/≥60, D/<60），阈值硬编码。即使总分计算修复，等级标准也无法按岗位/模板差异化。

**建议**：将等级阈值配置化，支持不同岗位/模板使用不同的等级标准。

#### 4.7 签名接口未校验签名者身份

**位置**：`sign()` 方法

**问题**：签名只接受 `signType` 和 `signName`，但没有校验：
- `signType=self` 时当前用户是否是该实例的员工
- `signType=supervisor` 时当前用户是否是该实例的上级

**建议**：增加身份校验，确保员工不能代上级签名，上级也不能代员工签名。

#### 4.8 签名 name 可随意输入

**问题**：`signName` 是纯文本字段，前端输入框允许任意输入。签名在人事意义上是严肃操作。

**建议**：至少校验 signName 与当前用户姓名一致，或增加更严格的签名验证（如密码确认、手写签名图片等）。

## 5. Dashboard 首页概览

### 当前逻辑

| 功能 | 状态 |
|------|------|
| 待办任务列表（自评/评分/签名） | ✅ |
| 数据概览统计（待办/完成/平均分/等级分布/趋势） | ✅ |
| 基于角色的快捷操作 | ✅ |

### 已发现问题

#### 5.1 待办任务判断中 supervisorId 空值无显式保护

**位置**：`todos()` 方法

**问题**：`inst.supervisorId === userId` 比较时 `supervisorId` 可能为 `null`，逻辑上没问题（null 不会匹配），但代码没有显式处理空值。

**建议**：对 `supervisorId` 为 null 的情况增加空值保护。

#### ★ 5.2 【P0】HRD 判定逻辑错误

**位置**：`buildShortcuts()` 方法

**问题**：判断是否为 HRD 的逻辑是：`empRows.length === 0 || empRows[0].supervisorId === null`。但刚入职未分配上级的员工也会被视为 HRD，这显然是错误的。

**建议**：增加角色字段（`role`）或部门字段判断，而不是通过"没有上级 = 最高权限"这种容易误判的逻辑。

#### 5.3 概览数据范围与角色不匹配

**问题**：`overview()` 只查询 `employeeId = userId` 的个人数据。对于上级用户，应该看到下属团队的概览数据；HRD 应该看全公司概览。

**建议**：根据角色返回不同的概览范围：
- 员工：个人数据 ✅ 当前正确
- 上级：下属团队数据
- HRD：全公司数据

### 已发现问题

#### 7.1 团队概览只统计直接下属

**问题**：`getOverview()` 只查 `supervisorId = userId` 的直接下属。多层组织架构下，部门负责人需要看整个部门的汇总数据。

**建议**：如果业务需要，改为递归查询所有层级的下属。

#### 7.2 催办消息缺少考核链接

**问题**：催办消息是纯 Markdown 文本，没有链接让员工一键跳转到考核页面。

**建议**：在消息中加入考核详情页链接（如果飞书消息支持跳转），或使用飞书卡片消息提供更丰富的交互。

#### 7.3 催办返回值缺少详情

**问题**：`remind()` 返回 `{ success: true }`，但可能部分实例催办失败，调用方无法知道。

**建议**：返回详细结果，如 `{ success: true, results: [{ instanceId: '...', status: 'sent' | 'failed', reason?: string }] }`。

#### 7.4 字段命名歧义

**问题**：`pendingSelfCount` 在实际语义上是"等待员工自评的考核数"，但对上级来说容易误解为"等待上级自评"。

**建议**：改为 `waitingSelfReview` 和 `readyForSupervisorReview`。

## 9. 跨模块横切问题

### 9.1 事务一致性

**发现多处缺少事务的场景：**

- 模板编辑（先删后插）
- 发布考核（批量创建实例 + 快照 + 审计日志）
- 自评/上级评分写入（多指标 upsert）
- 员工签名（更新签名 + 检查双方签名 → 更新状态）

**建议**：所有涉及多表写操作的接口都应使用 `db.transaction()` 包装。

### 9.2 用户身份鉴权缺失

**当前模式**：通过 `req.userContext.userId` 获取用户。写操作使用 `@NeedLogin()` 保证已登录。

**缺失的权限校验：**

| 接口 | 缺少的权限校验 |
|------|---------------|
| `submitSelfRating` | 未校验当前用户是否是该实例的员工 |
| `submitSupervisorRating` | 未校验当前用户是否是该实例的上级 |
| `sign` | 未校验签名者身份是否匹配 |
| `adjust` / `unlock` | 未校验当前用户是否有操作权限 |
| `remind` | 未校验当前用户是否是该实例员工的上级 |
| `deactivate template` | 未校验当前用户是否有操作权限 |
| `create/update template` | 未校验当前用户是否是 HRD |

**建议**：引入角色和资源级别的权限校验机制，而不是依赖前端路由限制。

### 9.3 共享类型与实际返回数据未完全对齐

**问题**：部分类型如 `EmployeeBindingItem.employeeId`、`BindingHistoryItem.operatedBy` 在后端实际返回的是 user_profile 格式，但类型标注为 string。

**建议**：统一类型定义与实际返回数据的对齐。

### 9.4 错误处理一致性

**问题**：部分接口返回 `{ success: boolean }`，部分直接返回数据对象，部分返回 HTTP 状态码异常。前端处理错误模式不统一。

**建议**：统一 API 响应格式，将 `success` + `data` + `error` 作为固定包装结构。

### 9.5 删除操作安全性设计良好，但缺少数据归档

**问题**：系统没有任何物理删除操作（全部软删除），符合审计要求。但废弃数据持续增长。

**建议**：未来引入数据归档策略。

### 9.6 权重校验双标

**问题**：前端创建/编辑模板时校验权重之和=1、满分之和=100。但发布时调整指标的维度权重硬编码为 0，绕过权重校验。

**建议**：在调整 API 中也执行权重和满分的校验，或明确调整模式不执行校验（需前端明确提示用户）。
